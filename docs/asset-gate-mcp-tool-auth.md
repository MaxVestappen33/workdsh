# WorkDSH MCP 工具级授权方案（定稿）

本文说明在现有「连接器粒度」资产授权之上增加「工具粒度」收窄的完整设计：授权模型、快照结构、判定点、界面、后台接口、发布要求、缺陷修复、风险与验收门槛。**实现状态（2026-11-12）**：客户端与后台代码已完成，单元测试、typecheck、后台离线编译、桌面端重建启动均通过；尚缺用真实白名单数据做的端到端验收（见第十四节末段）。

- 上游文档：[asset-gate-design.md](./asset-gate-design.md)
- 适用端：Desktop（企业登录态）。Web 预览端仍按《资产闸门设计方案》第十七节保持默认全关，不在本文范围。
- 范围：只覆盖 `mcp` 一类资产。技能、专家、专家团、模型、提示词的判定口径不变。

## 一、决策记录

| # | 决策 | 结论 |
| --- | --- | --- |
| 1 | 授权形态 | 连接器授权 + 授权分段内的工具白名单；工具只能做减法，不是独立授权单元 |

## 二、范围与术语

- **连接器**：后台 `ai_mcp_tool` 的一条记录，市场条目 id 即本文的「连接器编号」。
- **原始工具名**（rawName）：MCP 服务自己声明的工具名，存在 `ai_mcp_tool.tools[].name`。
- **公共工具名**（publicName）：客户端注册到工具运行时的名字，形如 `mcp__<serverName>__<rawName>`，可能被官方改写（见第六节）。
- **白名单**：某条授权分段对某连接器显式勾选的工具原始名集合。
- **收窄**：连接器已授权的前提下，进一步限制可用工具；收窄不会扩大权限。

## 三、授权模型

### 3.1 层级

授权单元仍是**连接器**。判定顺序固定为：连接器级通过 → 才看工具级。连接器级不通过时，工具级数据一律不读。

不把工具提升为独立授权单元的理由：连接器有安装、启停、进程、凭据、离线缓存等完整生命周期，提升到工具层会分裂成两套状态机，撤权账本、审计、市场过滤都要重写；而工具级只需要在判定时做一次集合裁剪。

### 3.2 三种语义

| 分段配置 | 语义 | 判定行为 |
| --- | --- | --- |
| 未选工具（`tool_auth` 中没有该连接器的键，或列表为空） | 全部工具 | 连接器级放行即全部放行（与当前行为一致） |
| 选了部分工具（非空列表） | 白名单 | 仅列表内工具放行，其余拒绝 |
| 连接器公开上架 | 全部工具 | 不做工具级判定 |

「空列表 = 全部工具」与管理端现有交互一致（清空多选框即全部），不额外引入「一个工具都不授权」的状态；确实要全部禁用时，应把连接器从授权分段中移除（那是撤权语义，不是工具收窄）。

### 3.3 公开与白名单的关系

公开上架在现有模型中等于「所有账号可用」，因此公开视作一条「全量虚拟分段」。多源并集时只要命中公开，结论就是全部工具。

后果必须写进运维说明：**在公开连接器上勾选工具白名单不会生效**。要让白名单生效，需先取消公开、改为按账号/部门/角色授权。

### 3.4 多源并集

对某账号的某连接器，收集所有命中的授权分段与「公开」标记：

1. 任一分段为「全部工具」，或连接器公开 → 结论「全部工具」；
2. 否则把各分段的白名单求并集；
3. 并集为空（只删工具不删连接器）→ 视为「无任何工具可用」：列表标注、调用一律拒绝。

### 3.5 新增工具

- 「全部工具」模式：新工具自动可用（保持现状，避免误伤存量连接器）。
- 「白名单」模式：新工具默认拒绝（fail-closed），需要管理员在后台「同步清单」后重新勾选。

这是全方案唯一会出现「后台没改、用户忽然不能用一个新工具」的地方，必须写进交付说明，并在管理端工具选择框附近提示。

## 四、数据模型

### 4.1 落库：复用现有列

后台已有 `ai_asset_auth_grant.tool_auth`（JSON，`{<连接器编号>: [<原始工具名>…]}`）与 `scope` 两列，管理端授权弹窗已实现逐工具多选与「同步清单」，因此**不新增表、不改表结构**。

需要补的只有写入侧校验与规范化：

- `tool_auth` 的键必须是本段 `asset_ids` 中出现的连接器编号，否则拒绝保存；
- 工具名长度 ≤128 字节、每个连接器 ≤200 个，超限报错，不做截断；
- 保存时对工具名去空、去重、排序（保证修订号稳定）；
- 非 `mcp` 分段继续强制清空 `scope` 与 `tool_auth`（沿用现有逻辑）。

`ai_asset_auth_grant` 的更新是「整段重建」（逻辑删旧行 + 插新行），`del_flag` 由 `@TableLogic` 处理，因此删除分段即工具授权一起失效，不会产生孤儿记录。

不新建「工具授权表」的理由：工具清单本身就是 JSON 列，再建一张授权表会出现两套一致性来源；工具级授权只在生成快照时被消费一次，当前没有按工具维度出报表的需求。若日后需要，再迁至 `(auth_id, mcp_asset_id, tool_name, del_flag)`，并配 PostgreSQL 部分唯一索引 `UNIQUE (auth_id, mcp_asset_id, tool_name) WHERE del_flag = 0`——逻辑删除必须带 `del_flag = 0` 条件，否则重建授权会撞唯一键。

### 4.2 快照结构（条目化）

`assets.mcp` 由字符串数组改为条目数组；其余六个类型保持字符串数组不变。

```jsonc
{
  "revision": "9f2c…",
  "unchanged": false,
  "staleAt": "2026-11-20 23:59:59",
  "generatedAt": "2026-11-12 10:00:00",
  "assets": {
    "skill": ["1857"],
    "mcp": [
      { "id": "2120326372515352577", "tools": ["search_docs", "read_doc"] },
      { "id": "2120058995689046017" }
    ],
    "expert": [], "expert_group": [], "model": [], "knowledge": [], "prompt": []
  }
}
```

条目字段：

| 字段 | 必有 | 含义 |
| --- | --- | --- |
| `id` | 是 | 连接器编号（后台 `ai_mcp_tool.id`），字符串，非空 |
| `tools` | 否 | 原始工具名数组。**缺省或空数组 = 全部工具**；非空 = 白名单 |

- 「公开 = 全部工具」的表达：公开连接器会出现在 `assets.mcp` 中但**不带 `tools` 字段**，与显式「全部工具」的授权分段输出完全一致；服务端在装配期就把「公开」折叠成「全量」，客户端不需要知道公开标记。
- 条目顺序：按 `id` 的字典序排序；同一连接器只出现一次。
- 只下发工具名，不下发描述、入参 schema、`toolCount`。
- `unchanged=true` 分支只返回 `revision`、`unchanged`、`staleAt`，不带明细。
- 其余六个类型保持 `string[]`，解析规则不变。

解析规则（客户端）：

1. `assets` 缺失或不是对象 → 抛 `asset-gate/response-invalid`，按快照获取失败处理（见第十一节）；
2. `assets.mcp` 不是数组 → 同上；
3. 条目不是对象、`id` 缺失/非字符串/空串 → 同上；
4. 条目 `id` 重复 → 取并集（工具列表合并去重），不视为错误；
5. `tools` 存在但不是字符串数组、或含空串 → 同上；
6. 其余六个类型不是字符串数组 → 同上（保持现有的全量校验口径）。

**不得把无法识别的结构静默降级成空集**。这是第十一节缺陷的直接成因。

### 4.3 修订号

`buildEntitlementRevision` 的输入必须包含工具明细，否则只改白名单、不改连接器集合时修订号不变，客户端带 `revision` 探测会一直得到 `unchanged`，白名单永不生效。

规范化拼接（固定顺序、可复现）：

```text
ai-asset-entitlement-v1|skill=<排序id,用逗号>|mcp=2120:read_doc,search_docs;2121|expert=…|…|stale=<时间>
```

- `mcp` 段按连接器 `id` 排序；
- 同一连接器内工具名排序；
- 无工具明细的连接器只写 `id`，不写冒号。

上线后修订号会变化一次（输入串格式变化），属预期。

### 4.4 体积与上限

快照是单个 GET 响应（审计上报的 256KB 上限不适用于此）。估算：100 个受限连接器 × 30 个工具 × 平均 25 字节 ≈ 75KB，可接受。

硬上限：每连接器 200 个工具、工具名 ≤128 字节，**在写入期拒绝**而不是下发时截断。截断会把「管理员勾了却不能用」变成不可解释现象，不如在保存时报错分批。

客户端在快照加载时把条目预编译为 `Map<连接器编号, Set<原始工具名>>`（无 `tools` 的连接器不入表，表示全部工具），判定阶段为纯内存查表。

### 5.3 「id 集合」与「工具明细」如何不再出现两套来源

改完后只有一份中间表示：**连接器条目数组**。

1. **后台**：`buildAssetIdsByType` 一次遍历同时产出「id 集合」与「id → 工具集合」；可见性过滤只对 id 集合做（`retainAll`），装配期用最终 id 集合去裁剪工具映射，最后一次性生成条目数组。条目数组是唯一对外表达，修订号也由它序列化——不会出现「修订号只反映 id」而工具变化漏检的情况。
2. **客户端**：`SnapshotRecord.assets.mcp` 的条目数组是唯一存储形态；`decider`、撤权对账、界面统计都从它派生：
   - 需要 id 集合时用 `entries.map(e => e.id)`（撤权对账、账本求交）；
   - 需要工具明细时用 `entry.tools`（工具判定、掩码、UI）。
   两者都是同一个数组的只读投影，不落第二份缓存，也不存在「字段 A 有 id、字段 B 有工具」的交叉校验问题。
3. **草稿期曾考虑的「并列字段 + 子集校验」被取消**，交叉不一致的结构性风险随之消失。

## 六、名字映射：正向推导

白名单里是**原始工具名**；客户端调用看到的是**公共工具名**，且官方在超长或含非法字符时会改写：

```text
publicName = `mcp__${serverName}__${rawName}`                    // 合规且 ≤64 字符
           = `mcp__${serverName}__${rawName}` 归一化后截断 + '_' + sha256(`${serverName}\0${rawName}`).slice(0,12)
```

官方明确「公共名不用于还原原始名」，因此**禁止反向解析**。采用正向推导：

```text
allowedPublic = whitelist.map(raw => publicToolName(serverName, raw))
deny          = 实际注册工具名(以 mcp__<serverName>__ 开头) − allowedPublic
```

这样重命名、截断、哈希三种情况都被自然覆盖，不需要映射表，也不需要安装时固化。

约束：

- 客户端需复刻上述 6 行纯函数（使用 `node:crypto` 的 sha256），并用单测向量锁死：无损名、含点号名、超 64 字符名、含中文名；
- 运行时自检：白名单模式下若「推导出的允许集合」与「实际注册工具」交集为空而该连接器确实有工具，视为映射不可信，**全量拒绝**并记 `gate/denied-mapping-untrusted` + 一条 warning；
- 该函数若随官方升级变化，表现是「工具被误拒」而不是「被误放」，方向安全；
- `serverName` 取连接器记录里的本地标识（市场安装时由 serviceId 换算，规则确定）。

## 七、判定点与审计

| 位置 | 行为 | 拒绝码 | 审计层 |
| --- | --- | --- | --- |
| 数据层：安装、启停、市场列表 | **不判工具**。装了但只开放一个工具是合法状态 | — | — |
| 可见层：`agent.ctx.tools.restrict` | 不在白名单公共名内的工具从模型可见集合中移除 | 无（不可见不产生事件） | — |
| 执行层：`tools/pre-execute` + `ctx.tools.guard` | 连接器级放行后再判工具；两层口径一致 | `gate/denied-tool-not-entitled` | `call_tool_item` |

补充约定：

- 可见层不产生审计。隐藏不是「被拒绝」，记事件会让统计口径失真（与技能目录裁剪不审计一致）。
- 执行层是权威边界。模型可能从历史上下文拿到旧工具名并尝试调用，必须由双层钩子兜底（沿用现有 `pre-execute` 记结果表 + `guard` 同步复述的结构）。
- 连接器级拒绝仍记 `call_tool`；工具级拒绝记 `call_tool_item`。混用会让「整服务撤权」与「单个工具不在白名单」无法区分。后台 `layer` 是自由字符串列、仅维护注释，无需枚举变更（与 `call_skill_inject` 先例一致）。
- 审计字段：`assetType='mcp'`、`assetId=<连接器编号>`、`toolName=<公共名>`（≤64，后台限长 200）。
- 判定异常（读快照、推导名字、查表抛错）统一按 `gate/denied-evaluation-error` 拒绝，不放行。

新增原因码：

| 原因码 | 文案 | 场景 |
| --- | --- | --- |
| `gate/denied-tool-not-entitled` | 当前账号未获得该工具的使用授权。 | 白名单不含该工具 |
| `gate/denied-mapping-untrusted` | 工具与授权记录的映射不可信，已拒绝。 | 白名单无法正向推出任何可用公共名 |

`gate/denied-mapping-untrusted` 此前已在码表预留，本方案是它的第一个产生路径。

## 八、界面

- **连接器卡片**（本地管理）：受限时在来源标签后加 `部分工具 · 3/7`（可用/实际），不新增按钮、不改变启停语义。
- **连接器详情**：工具列表逐条展示，未授权项置灰 + 行尾「未授权」+ 悬浮原因（文案取自同一码表）。
- **市场卡片**：标注「部分工具可用」，并提示安装后可在详情查看具体工具。
- **不做客户端逐工具勾选**：授权只在后台管理端配置，客户端只读展示。
- **模型侧隐藏、界面置灰**：置灰对人有解释价值；对模型展示调不动的工具只会浪费一次工具往返。
- **管理端**：工具选择框补充提示「公开上架的连接器按全部工具放行，如需按工具细分请先取消公开」；保留已有的「同步清单」与 stdio 手工维护提示；授权列表的「仅授权工具：…」展示保留。

## 十、发布要求与兼容

### 10.1 同时发版

`assets.mcp` 结构变化是契约变更，客户端与后台**同一版本发布即可**，不需要灰度编排，也不需要格式协商：

- 后台把快照改为条目数组的同一个版本里，客户端具备条目解析与工具级判定；
- 不保留「旧字符串数组」兼容分支，也不做 `format=v2` 之类的参数协商——没有需要兼容的对象，保留双形态只会长期多养一条不常走的代码路径；
- 发版后管理员即可开始配置工具白名单，配置即生效（第十二节）。

### 10.2 说明性备注：更早的安装包

已经发布的安装包都不包含资产授权闸门逻辑，因此不存在「旧客户端把条目读成空数组」的真实场景。这里只作为背景说明保留：

- 若把条目结构的快照交给一个只认字符串数组的旧解析器，它会把条目对象丢弃，得到空的 `assets.mcp`，随后连接器全部判未授权，并可能触发批量撤权（第十一节）；
- 这不构成发布约束，也不是选择 B 的代价。它只说明第十一节的失败路径为什么必须修——**任何**把未识别结构静默降级为空集的解析实现都会产生同类后果。

## 十一、独立缺陷：空快照 / 非法快照触发批量撤权

本节是一个**与 A/B 选择无关的独立缺陷**，无论最终快照形态如何都应修复；B 只是让它更容易被触发。

### 11.1 现象与成因

`AssetGateService.pull()` 拿到「结构上有效、但结论为空」的快照时，会照常执行 `reconcileRevocations`，把「已安装 − 快照」全部判为撤权。触发路径至少三条：

1. 解析器把不认识的条目静默丢弃，得到空集合（任何不认识条目结构的解析实现，含未来可能出现的降级分支）；
2. 后台装配异常或上游数据异常，返回了七类空数组的「合法空快照」；
3. 任何导致 `assets` 被读成空的解析降级。

三条路径的后果相同：批量撤权 + 写账本 + 停进程 + 落审计，且不会自动回滚。

### 11.2 修法（P0，独立于本方案）

1. **解析层严格化**：`assets` 或任一类型不是可识别结构时抛 `asset-gate/response-invalid`，**不得降级为空集合**。缺失字段与非法结构必须区分：字段整体缺失按协议错误处理，类型内数组为空才是真正的「无授权」。
2. **失败保留旧快照**：拉取或解析失败时沿用上一份成功快照（现有 `pull()` 已返回 `cached`），并且**不进入对账**：不写撤权账本、不调用 `applyGateState`、不停进程、不产生 `revocation` 审计。
3. **对账前置条件**：`reconcileRevocations` 只接受「本轮完整解析成功且通过结构校验」的快照；`unchanged` 命中也算成功（沿用现有口径），但必须来自一次真实的成功响应。
4. **可选加固（建议，不强制）**：单次对账若「撤权集合 = 全部已装集合」且该账号此前从未有过撤销记录，延迟一轮（下一次成功快照）再执行，连续两轮结论一致才落账本，并记一条 warning。真实场景中管理员一次性撤掉全部授权是合法的，因此只能延迟确认，不能永久拒绝。

### 11.3 验收

- 构造「结构非法」的回包：客户端保留旧快照，无新增账本条目、无 `revocation` 审计、进程不停；
- 构造「七类空数组」的合法回包：按现有语义执行撤权（这是真实撤权，不拦截），但要有 warning 与可查审计；
- 回归现有撤权用例：正常撤权/恢复行为不变。

## 十二、时效性与回退

### 12.1 生效时效

复用 `mcp` 子闸门后没有额外开关，链路为：

```text
后台保存白名单
 → 客户端下一次 revision 探测（周期 60 秒）
   或触发点（进入市场页签 / 点刷新 / 窗口重新聚焦 / 安装·启停·卸载完成；单飞 + 15 秒节流）
 → 修订号变化 → 拉全量快照 → 重算工具掩码
 → 下一次工具调用即按新白名单判定
```

- **最迟 60 秒、通常一个请求往返**即生效；后台一配白名单，客户端下一轮快照就收窄。
- 已在进行中的会话：执行层每次调用都查内存快照，**立即生效**；模型可见工具清单在掩码重算后生效。
- 与既有「授权实时性」要求一致：工具级走的是同一条快照通道，没有引入更慢的路径，也没有新增缓存层。
- 前置条件：`connectors` 的连接器管理器必须在每次快照对账后**无条件**重算工具掩码（见 5.1）；否则会出现「执行层已拒绝、模型仍看得见」的错位。

### 12.2 回退方式

- **粒度**：每个连接器 × 每个授权分段。
- **操作**：清空该分段的工具选择（`tool_auth` 中该连接器的键置空或删除）。
- **效果**：下一轮快照（≤60 秒）恢复「全部工具」，无需发版、无需重启、无需改表。
- **注意**：把连接器从授权分段移除 ≠ 清空白名单。前者是撤权，会触发撤权账本、停用进程、写 `revocation` 审计；回退时应只清工具选择，不动 `asset_ids`。
- **没有独立开关的代价**：配错立即生效，回退窗口以一次快照同步为限。缓解方式：管理端保存前二次确认影响面（命中的账号/部门/角色数量），保存后提示「已生效，最迟 60 秒同步到客户端」。授权编辑本身已有操作日志可回溯。

## 十三、风险与缓解

1. **工具名映射漂移**（改配置、重装、换机、服务端升级工具名）
   缓解：正向推导 + 运行时交集自检；无法映射一律拒绝（宁误拒不误放）；管理端标出「授权里有、清单里没有」的悬空工具名；详情页对受限连接器提示「需在后台重新同步工具清单」。
2. **工具清单过期**（未同步；stdio 靠人工维护）
   缓解：展示清单更新时间；`toolCount` 与实际注册数不一致时提示「清单可能过期」；白名单固定 fail-closed；不提供「未知工具自动放行」开关。
3. **快照体积与解析成本**
   缓解：只下发受限明细、每连接器 ≤200 工具、名字 ≤128 字节；客户端加载时预编译为 `Map<id, Set<rawName>>`，判定纯内存查表；超限在写入期拒绝。
4. **空快照批量撤权**（第十一节）
   缓解：解析严格化 + 失败不对账 + 可选的一轮延迟确认。这是独立缺陷，必须先修。
5. **模型侧与应用侧枚举不一致**
   缓解：可见层只做减噪，执行层才是边界；对账后无条件重刷掩码；判定异常按 `denied-evaluation-error` 拒绝；`exec.agent` 为空（Host 内部调用）继续放行。
6. **公开与白名单语义冲突**
   缓解：固定「公开 = 全部工具」，在管理端提示、本文档、变更评审三处写死，不提供第三种解读。

## 十四、验收门槛

**单测**

- 条目解析：缺 `assets`、`assets.mcp` 非数组、条目非对象、`id` 缺失/空、`tools` 非字符串数组、六类结构非法 → 全部抛协议错误；重复 `id` → 合并去重。
- 判定矩阵：主闸门关、`mcp` 子闸门关、条目缺失、条目无 `tools`、`tools` 命中、`tools` 未命中、映射不可信、判定抛错。
- 公共名推导向量：无损名、含点号、超 64 字符、含中文四组；与运行时实际注册名一致的断言。
- 修订号稳定性：只改工具列表必须改修订号；工具顺序变化不改修订号。
- 撤权对账：条目数组投影出的 id 集合与原行为一致；工具收窄不产生撤权标记。

**端到端**

- 白名单内工具可调用；白名单外被拒，审计落 `call_tool_item` + `gate/denied-tool-not-entitled`。
- 连接器整服务撤权仍落 `call_tool` + `gate/revoked-authorization`。
- 公开连接器配白名单仍全量放行（验证第 4 条决策）。
- 白名单模式新增工具默认拒绝；同步清单并勾选后可用。
- 清空白名单后 ≤60 秒恢复全部工具。
- 空快照且本地无已装资产：一次无副作用的空同步（不生成账本、不产生撤权标记）；有已装资产时按「本地已装 − 空快照」全部标记撤权并停用，授权恢复后账本自动清空并落 `write|revocation|restore|success`（`remark=auto-restored`）。
- 结构非法回包：保留旧快照、不写账本、不停进程（第十一节）。

**性能与关闭态**

- 主闸门关或 `mcp` 关时：不读条目、不推导名字、不注册新逻辑、不产生新审计，工具枚举耗时不变。
- `mcp` 开但快照无工具明细时：行为与今天完全一致。
- 100 个受限连接器 × 30 工具的本地判定耗时在可忽略量级（内存查表）。

**时效**

- 改白名单后无需新建会话：执行层立即生效；可见层在快照对账后收敛（验证 5.1 的「无条件重刷掩码」）。

## 十五、工作量粗估

| 端 | 文件数 | 规模 | 主要改动 |
| --- | --- | --- | --- |
| 后台 | 3 | 中 | 快照装配 + 修订号（`AiClientServiceImpl`）、授权写入校验（`AiAssetAuthServiceImpl`）、工具映射在装配期的一次性附着；无新表、无新策略行 |
| 客户端 asset-gate | 5～6 | 中 | 类型与解析、判定器（含 `decideTool`）、服务 API、撤权对账投影、执行层、原因码 |
| 客户端 connectors | 4～5 | 中 | 工具策略查询与公共名推导、对账后无条件重刷掩码、`summary` 工具统计、卡片/详情/工具列表展示 |
| 契约 | 1 | 小 | `ConnectorSummary` 增加工具授权字段 |
| 管理端 Vue | 0～1 | 小 | 仅补公开语义提示（逐工具勾选已存在） |

## 十六、明确不做

- 不做格式协商（`format=v2` 之类的参数）、不保留并列 `mcpTools` 字段。
- 不新建工具授权表、不改 `ai_asset_auth_grant` 表结构。
- 不新增 `mcp_tool` 子闸门、不加策略行、不做独立灰度开关。
- 工具不进入撤权账本：一个工具被移出白名单不停整个连接器进程。
- 不做客户端逐工具勾选；不做「未知工具自动放行」兜底。
- 不改官方运行时：不修改 `dsh-mcp-client`，只按其公开的命名不变量正向推导。
- 不动 `scope` 字段：它是 MCP 的数据查询范围，与工具白名单正交，不得混用。

## 十七、实现顺序建议

1. **先修独立缺陷**（第十一节）：解析严格化 + 失败不对账。这一步不依赖任何结构决策，且能立刻降低后续上线的爆炸半径。
2. **改契约与解析**：`types.ts` / `snapshot.ts` / 后台 `queryEntitlementSnapshot` + `buildEntitlementRevision`，此时不要接判定，只让新结构能完整往返（可先写单测）。
3. **接入判定**：`decider.decideTool` + `enforcement.ts` 工具分支 + 新原因码 + `call_tool_item` 审计。
4. **接入可见层与界面**：连接器管理器的公共名推导、掩码重刷、`summary` 统计、卡片与详情。
5. **管理端提示与写入校验**：`saveGrants` 的键/长度校验、公开语义提示。
6. **端到端验收与发版**：按第十四节逐条跑；客户端与后台同一版本发布，发版后再开始配置白名单。
